# Native certificate validation

The `x509-native` feature exposes two offline Rust APIs, using only first-party
and IronCrypto crates. `attestation` includes this feature. These APIs are not
new CLI/MCP tools and do not implement a TLS transport.

- `x509::verify_endorsement_certificate(leaf, anchors, intermediates, now)` checks
  a certificate path for TPM endorsement-key usage. It does not bind the public
  key to a TPM, verify TPM certifications or perform credential activation;
  use the existing attestation workflow for those checks.
- `x509::verify_tls_server(leaf, anchors, intermediates, now, expected_server)`
  checks the path for TLS server usage and the leaf's DNS or IP subjectAltName.
  Key usage, if present, must allow digital signatures. It targets signing TLS
  handshakes, not legacy static RSA key exchange.

Both return the index of the accepted caller-supplied root certificate. Inputs
are complete DER certificates and a trusted Unix timestamp in seconds. Callers
must independently select their roots and expected server; do not learn either
from untrusted certificate metadata. EK and TLS extended usages are separate:
when EKU is present, it must explicitly include the requested purpose. Absent
EKU is unrestricted. An intermediate's EKU also restricts the path.

Server matching uses ASCII DNS A-labels or bare IPv4/IPv6 addresses. DNS matching
is case-insensitive and accepts one terminal dot in the reference host. Wildcards
must be the entire left-most label and have at least two literal labels following
them; they match exactly one label. There is no Common Name, URI-ID or SRV-ID
fallback. Numeric IP identities require matching binary IP SANs, not DNS SANs.
URLs, ports, userinfo, scoped/bracketed IPv6, Unicode host labels and wildcard
reference hosts are rejected. No IDNA conversion or public suffix list is used.

The [native attestation profile](ATTESTATION.md#native-certificate-profile) gives
the shared signature, path, critical-extension and size limits. Applicable
unsupported name constraints fail closed, including wildcard DNS SANs under DNS
constraints. Verification checks every applicable SAN against ancestor constraints,
not just the SAN that matches the requested host. No CRL/OCSP checks, network
fetching, implicit roots or policy-tree processing occur.

Certificate verification alone does not establish a TLS connection or possession
of the certificate's private key. A TLS engine must still authenticate the
handshake transcript, peer proof of possession and Finished before releasing
credentials or application data. Verification never authorizes host actions.
Independent PyCA fixtures cover accepted and rejected identities, usage separation,
signatures, missing roots and chain constraints; independent review is outstanding.

KMS continues to use rustls with IronCrypto for TLS 1.2/1.3. Its public root data
is now [bundled with provenance and an update procedure](../data/README.md),
preserving the former trust set exactly. That data uses DER sequence contents,
so it is not directly interchangeable with this API's full-certificate inputs.
The optional [native TLS 1.3 client](TLS.md) now uses these full-certificate APIs
for its experimental, explicitly configured Rust interface. KMS migration remains.

KMS certificate rejection is a non-retryable `key_not_trusted` error; other TLS
validation failures are non-retryable `authentication_failed` errors. Obtain
operator review rather than adding peer certificates or weakening checks.
The independent local TLS 1.2/1.3 rejection test checks that an untrusted server
receives no application bytes and that no key file is published.
