# Certificate validation

IPG validates certificates through
[IronPKI](https://crates.io/crates/ironpki), the IronSecurity stack's
certificate layer, which IronSocketLayer also uses. IPG's own X.509 parser and
path validator were removed in its favour, so the stack has one.

## What IPG exposes

The `x509-native` feature, which `attestation` includes, exposes one offline
Rust API. It is not a CLI or MCP tool.

`x509::verify_endorsement_certificate(leaf, anchors, intermediates, now)` checks
a certificate path for the TPM endorsement-key purpose and returns the index of
the caller-supplied root that accepted it. It does not bind the public key to a
TPM, verify TPM certifications or perform credential activation; the
[attestation workflow](ATTESTATION.md) does those.

Inputs are complete DER certificates and a trusted Unix timestamp in seconds.
Callers select their roots independently; a certificate is never trusted because
it was presented. Malformed anchors are never used, and a leaf is accepted only
by a verified path, never because it is itself among the anchors.

IPG no longer offers `verify_tls_server`, `verify_tls_server_anchors` or
`x509::TrustAnchor`. They served IPG's former TLS client. For TLS server
certificates, use IronPKI directly (`ironpki::x509::verify_chain` with
`Purpose::TlsServer`, then `verify_name`). Its rules differ from IPG's former
ones in three ways that IPG's vectors found, each deliberate on IronPKI's side:

- a certificate DNS name with a trailing dot names the same host as the name
  without it, where IPG never matched one (kept by IronPKI's maintainer);
- `anyExtendedKeyUsage` satisfies the TLS purposes, as RFC 5280 defines it,
  where IPG required the server purpose explicitly;
- a wildcard name under DNS name constraints is evaluated against every name
  it can match, where IPG refused every wildcard under constraints.

## How IPG configures IronPKI

| Setting | Value |
| --- | --- |
| Purpose | `TpmEndorsementKey`: an extended key usage, if present, must contain `2.23.133.8.1`; `anyExtendedKeyUsage` does not stand for it; the leaf must not be a CA |
| Signature algorithms | ECDSA P-256/SHA-256 and P-384/SHA-384, Ed25519, RSA of at least 2048 bits with PKCS#1 v1.5 or PSS and SHA-256/384/512. P-521, ML-DSA and SHA-1 are refused |
| Bounds | 64 anchors, 64 intermediates, 8 certificates below the anchor, 256 signature checks, 64 KiB per certificate |
| Time | The caller's timestamp; anchors' own validity is not checked, as in RFC 5280 |
| Name constraints | DNS, IP and rfc822Name constraints are evaluated; rfc822Name constraints also govern `emailAddress` attributes in the subject. Directory-name constraints govern the subject and directory-name alternative names: ASCII PrintableString and UTF8String values are compared without regard to case or spacing, anything else byte for byte, and a comparison that cannot be decided never favours the certificate. URI constraints govern the URI's host, and a URI without a DNS host is refused wherever one applies |
| Revocation | Not checked |
| Anchor as leaf | Refused |

Unknown critical extensions refuse the certificate. Certificate policies are
processed as RFC 5280 section 6.1 describes, with its default inputs: any
policy is acceptable and none is required until a CA in the path requires one.
From there a policy must be valid down to the leaf, or the path is refused.
IPG cannot name the policies it accepts. Nothing is fetched.

## Errors

| Failure | IPG error |
| --- | --- |
| Malformed or unsupported certificate, or an unknown critical extension | `invalid_format` |
| No verified path, wrong purpose, expired, constraint violation | `key_not_trusted` |
| No anchors supplied | `invalid_request` |
| More than 64 anchors or 64 intermediates | `limit_exceeded` |

## Evidence

Independent PyCA fixtures check IPG's use of IronPKI: 40 path cases
(`tests/vectors/x509-paths.json`: missing and wrong issuers, CA and key-usage
rules, path lengths, DNS, IP and directory-name constraints, and certificate
policies) and 10
endorsement-key policy cases
(`tests/vectors/attestation-certificate-policy.json`). The verdicts are the
ones IPG's former validator gave, except for directory-name constraints,
which IronPKI evaluates from 0.1.2 and which have three cases (a permitted
subject, a subject outside the permitted name, and an excluded subject), and
for certificate policies, which it processes from 0.1.3 and which have eight
(a required policy asserted, absent and different; anyPolicy allowed and
inhibited; a critical inhibitAnyPolicy; a malformed extension). These
are a regression baseline, not a complete X.509 conformance suite. IronPKI
carries its own interoperability tests against OpenSSL; neither it nor IPG's
use of it has had an independent review.
